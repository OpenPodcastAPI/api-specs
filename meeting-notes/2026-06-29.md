### Authentication & log-in approach: [9340105](https://github.com/OpenPodcastAPI/api-specs/blob/934010532b93ef9679ebe511d1ad982551cd1aa3/src/content/docs/specs/authentication.md)


* Why “simplified” OAuth flow instead of just using standard auth methods?

Is there a standard version of the log-in flow, that we could point to?

It's up to the server dev to select the auth method. From a spec perspective we can write: support at least JWT (bearer token) and/or OAuth (which requires a web browser) and/or basic auth (base64 encoded username & password - which is not ideal but encrypted over https, which would not require a roundtrip).

A client gets a password from the user, if the user accepts it, a bearer token can be used.

Documented in PR right now is based on JWT. Maybe we can specify that we recommend either having basic auth or OAuth. Downside of giving server devs choice: each client would have to implement support for multiple methods. Then we would use BasicAuth as mandatorily supported option - we don't need airtight security that OAuth provides as we don't handle sensitive data.

Potential benefits of OAuth?
* Uses a separate authentication server, which means that user identity is managed by some other service. There may also be servers which don't have a password at all but only use 'magic login' links.
* AntennaPod wouldn't know your password, and user might not have to retype the password if the user is already logged in (while with BasicAuth you'd certainly have to retype it).

We don't need too many scopes, at least not at this time - for now just `admin` and `user`. Maybe in future we could have slightly more granularity.

OAuth requires you either to have a social login provider (Google, GitHub) or create an account on the server. If not relying on a third party, the server would have to be the OAuth server & identity provider, which would mean additional work for the server dev to implement compared to BasicAuth.

If we go for BasicAuth now, we can add/replace with OAuth later. However, directly going for OAuth would be future-proof, and would avoid requiring a rewrite.

**DECISION**: we go with OAuth.

## Endpoint split

Single `sync` endpoint vs `subscriptions`+`episodes` endpoints ([discussion](https://github.com/orgs/OpenPodcastAPI/discussions/189#discussioncomment-17556719)).

Inspired by previous conversation and additional reading, limiting the batch sizes (30 items per batch) and reducing the number of calls.

When doing updates, the client would have to get updates with a 'what has changed since this time UTC' (timestamp as paginator). Two options:
* do at resource level: first subscriptions, then episodes
* do centralised call, with firehose with all changes (whether it's subscription or episode)

Apart from Subscriptions and Episodes, we might also need support/an endpoint for Queues.

With a central sync endpoint, there would be a router at server level. This would be a good way to receive all data at once - as client developer you'd need only to implement support for one endpoint.

You also need to first get updates before you push changes. So that's two calls per endpoint. I.e. 6 calls to push updates for subs, episodes & queues, versus 2 calls with a single update.

Having resources available at their specific endpoint would still make sense. Still have GET endpoints for resource (current state of a given episode/podcast) *and* GET endpoint for sync (ledger; record of changes to resources over time), but allow POST/PATCH actions only via sync.

Potential argument for only having resource-based endpoints: If there's two systems to implement, there's more things the server can do wrong.

Two concerns with resource-based endpoints:
* number of requests (see above)
* timing of events (sync could be sent in chronological order, with separate calls timing is more tricky)

Requirements from server dev perspective, implementation of the two aren't too different.

A web-UI could use the same endpoints for stateless operation. Only responsibility of sync endpoint: send *paginated* status changes (since timestamp) and receive status changes. Stateless web-UI could use only a) sync endpoint to send changes, and b) resource endpoints to always get current status. (That's also the approach taken in the subscriptions rewrite in `subscriptions-refux`.)

Given our focus on sync, we could say that sync enpoint is core and resource-specific endpoints are optional.

**DECISION**: we prioritise the sync endpoint, but leave in the resource end-points and mark them as optional.
